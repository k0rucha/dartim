# 学習ログ運用ワークフロー

このプロジェクトでは、開発プロセスそのものを学習教材として資産化します。
AIエージェントは、エラー解決や技術的な質疑応答が発生した際、**ユーザーの指示を待たずに** 自律的に `learning_log.md` を更新してください。

## ⭐️ 品質基準 (Quality Standards)
単なる「エラーログ」ではなく、**「技術的背景」と「概念の理解」** に重点を置いてください。
ユーザーが「次に同じ問題に直面したとき、自力で解決できる（あるいは回避できる）」レベルの深い理解を提供することを目標とします。

### 必須要素
1.  **現象 (Phenomenon)**: 何が起きたか。エラーメッセージだけでなく、ユーザーが書きがちな間違ったコード例などもあればベター。
2.  **原因 (Cause)**: なぜエラーになるのか。ライブラリの仕様、言語の特性、設計思想（Options Pattern, Builder Patternなど）まで掘り下げて書き記すこと。
3.  **解決策 (Solution)**: 正しいコード。
4.  **学び (Learning)**: 一般化された教訓。「～の時は～を使う」「～という概念で理解する」といった抽象化された知識。

## 💡 推奨テクニック
- **メタファー (比喩)**: 複雑な概念（Future, Stream, Contextなど）には、直感的な比喩（整理券、回転寿司など）を用いて解説を添えること。
- **Whyの追求**: 「仕様です」で終わらせず、「なぜ作者はその仕様にしたのか？」という設計背景（メモリ効率、安全性、拡張性など）まで考察し言及すること。
ただし、本当の設計思想は開発者のみぞ知ることなので、調べても開発者の意図がわからない場合はあくまでも考察であることを明示的に宣言してください。

## フォーマット例

```markdown
### N. [タイトル]
- **現象**: [具体的なエラーや、ユーザーの疑問点]
- **原因**: [表面的な理由だけでなく、アーキテクチャや設計思想レベルの深い理由]
- **解決策**: [具体的な修正コードやアプローチ]
- **学び**: [今後応用できる一般化された知識。比喩を用いた概念説明もここに記述]
```

## トリガー (いつ更新するか)
- エラーを解決した直後。
- ユーザーから「これは何？」「なぜこう書くの？」という概念的な質問があり、それに回答した後。
- 新しいライブラリやツール (ffmpeg, yt-dlp) を導入した際の設定メモ。
